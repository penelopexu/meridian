## 它能做什么

- **万年历** — 1900–2100 农历、二十四节气、干支纪年、生肖，公历农历双向互转
- **多历法** — 除中国农历外，还支持韩国檀纪、日本和历、伊斯兰历、希伯来历、印度历、波斯历、佛历、科普特历、埃塞俄比亚历、民国纪年，共 12 种
- **中国节假日** — 法定放假与调休补班逐日内置（依据国务院办公厅通知），另含传统节日与节气
- **国外节日** — 28 个国家/地区的节日规则，含复活节推算，按所选地点自动切换，也可手动指定地区
- **天气** — 当前实况、今明逐时（15 分钟粒度）、未来 7 天、过去 3 天实测，含海拔、紫外线、空气质量
- **穿衣建议** — 结合体感温度、风速、湿度、紫外线、海拔与昼夜温差的本地规则引擎
- **历史天气** — 可查到 **1940 年**，支持单日、区间折线图、历年同期对比
- **气象预警** — 中央气象台（大陆，县级）、香港天文台、美国国家气象局、德国气象局、中央气象台台风网，五个官方源全部免 key 直连；另可选和风；覆盖不到的地区按中国气象局阈值本地推算
- **时区换算** — 左右对称双向换算，自动处理夏令时
- **四种视图** — 日 / 周 / 月 / 年，年视图 12 个月一屏总览
- **多地点收藏** — 主收藏地点在打开时默认显示
- **9 种语言** — 简体中文、繁體中文、English、日本語、한국어、Español、Français、Deutsch、العربية（含 RTL 布局）
- **无障碍** — 语义化 landmark、键盘可操作、焦点可见、响应「减少动态效果」与「提高对比度」系统设置

## 两种用法

### 单文件版（最省事）

从 [Releases](https://github.com/penelopexu/meridian/releases/latest) 下载 `天时-单文件-带图标.html`，双击用浏览器打开。

一个 400 KB 的文件，字体、样式、脚本、144 座城市离线库、2885 条中国区县映射、1900–2100 农历表全部内嵌。拷到 U 盘能用，发给朋友能用。日历、农历、节气、节假日、阴阳历互转**完全不需要联网**，只有天气要上网。

### PWA 版（可安装到桌面/手机）

访问 <https://penelopexu.github.io/meridian/>，浏览器地址栏会出现「安装」图标。装完像原生应用一样有独立窗口和图标，且离线可用。

> 部署到自己的域名？见 [docs/域名与部署.md](docs/域名与部署.md)


## 数据来源与精度

- 天气与历史数据：[Open-Meteo](https://open-meteo.com/)，免费、无需 API Key、CC BY 4.0
- 历史数据为 **ERA5 再分析**，约 25 km 网格，**不是气象站实测**。城市尺度可用，山区与海岸线附近会有偏差；最近两天为 ERA5T 预备版，之后可能被回补修正
- 农历与节气为离线天文算法（太阳视黄经迭代求解），已对 1900–2100 全区间做往返一致性验证
- 中国法定节假日 2024–2026 逐日内置；未公布年份按法定节日推算并在界面标注「预估」
- 行政区划映射来自 [modood/Administrative-divisions-of-China](https://github.com/modood/Administrative-divisions-of-China)（民政部数据），2885 条县级 → 地级市

### 一个已知的未解问题：农历与 ICU 的分歧

本项目的农历引擎与浏览器内置 ICU 的 `chinese` 日历在 1901–2099 约 7.2 万天里有 **300 天日序不同、177 天仅闰月标号不同**，集中在 13 个年份。

凡是能与公开历书核对的锚点（1954 年春节 2 月 3 日、2027 年春节 2 月 6 日、1987 年闰六月），**本引擎均与历书一致而 ICU 不一致**。但我没能写出独立可信的天文仲裁程序来最终裁定其余分歧，所以这里如实标注为未决。

完整差异清单在 [`docs/lunar-vs-icu.tsv`](docs/lunar-vs-icu.tsv)。**懂历法的朋友非常欢迎来看** → [提 issue](https://github.com/penelopexu/meridian/issues/new?template=lunar-discrepancy.yml)

## 体感温度与穿衣建议是怎么算的

**体感温度用分段模型，每段只在各自公认的有效区间内使用：**

| 条件 | 采用公式 | 出处 |
|---|---|---|
| 气温 ≥ 27°C | 热指数 Rothfusz 回归式 | 美国国家气象局 NOAA |
| 气温 ≤ 10°C 且风速 > 4.8 km/h | 风寒指数 JAG/TI | 2001 年美加联合修订 |
| 10 ~ 27°C | 以气温为准，按风、湿、日照、降水小幅修正 | — |

**为什么不直接用接口给的 `apparent_temperature`**：Open-Meteo 用的是澳大利亚体感温度公式（Steadman 1994），它是为热应激评估设计的，在 20–27°C 会过度放大湿度权重。实测 25°C + 98% 湿度 + 3 km/h 风，该公式给出 30.6°C，但实际体感接近气温本身。中间这一段国际上没有权威的湿度订正公式，各国气象部门通行做法就是直接报气温。

**穿衣档位（11 档，从「酷热」到「极寒」）是本工具自定的经验表，不是任何标准。** 冷暖感受因人、因适应程度差异很大，界面上提供「怕冷 / 正常 / 怕热」三档整体校准，各偏移 ±2.5°C。

## 数据源与分辨率

### Open-Meteo 在各地的实际网格（实测）

撒点探测格心间距反推出来的：

| 地区 | 网格 | 背后模式 |
|---|---|---|
| 纽约 | ~0.8 km | HRRR 3 km |
| 柏林 | ~1.4 km | ICON-D2 2.2 km |
| 巴黎 | ~1.5 km | AROME 1.3 km |
| 伦敦 | ~2.0 km | UKMO UKV 2 km |
| 悉尼 / 莫斯科 | 3–4 km | |
| 东京 / 首尔 | 5–6 km | JMA MSM 5 km |
| 新加坡 / 拉各斯 / 孟买 | 8–9 km | 全球模式 |
| **中国** | **9.6 km** | 只有全球模式 |

欧美能到公里级，是因为 NOAA、DWD、Météo-France、UKMO 把各自的中尺度模式开放了数据。中国气象局的 CMA-MESO（3 km）未开放，Open-Meteo 只有 15 km 的全球版。所有 2–3 km 区域模式（ICON-D2、AROME、HRRR、UKV、JMA MSM）在中国境内都返回 "No data available"。

> 注：这些数字是格心间距反推的。HRRR 用兰勃特投影、ICON-D2 用旋转网格，换算成经纬度后间距不均匀，所以实测值比模式标称更细。有效分辨率仍以模式标称为准，但量级结论成立。

### 两项免费优化（已默认开启）

- **`cell_selection=land`**：沿海地点默认可能被分到海上格子。实测三亚 nearest 27.9° vs land 30.2°，差 2.3°；青岛栈桥差 1.6°。
- **`minutely_15`**：15 分钟粒度，界面上是「今明逐时」曲线。只取 48 小时（8 天要 29 KB，48 小时只要 9 KB）。

### 可选：和风天气格点（3–5 km）

在「数据源」面板填入自己的 API Host 和 API Key 即可切换，凭据只写入本机 localStorage。免费订阅 1000 次/天、QPM 100，含格点实况 + 24 小时逐小时 + 3–7 天逐日。

调用失败会**静默回退**到 Open-Meteo 并在面板里显示原因，不会让界面卡住。

需要注意：

- 和风格点是模式降尺度产物，官方文档明说「不能直接和气象站实测比」。**网格细不等于预报准**——用和风查柏林未必比 Open-Meteo 直连 ICON-D2 准，后者是德国气象局原生中尺度模式。
- 和风公告 2027-01-01 起会限制 API KEY 方式的每日请求量，届时需改用 JWT。

## 地名搜索

### Open-Meteo 中文索引不完整，必须中英双查

实测发现 `language=zh` 的索引缺失严重：

| 查询 | 中文索引返回 | 英文索引返回 |
|---|---|---|
| `new york` | 纽约市完全不在结果里 | New York 8,804,190 ✓ |
| `纽约` | 零结果 | — |
| `东京` | 只有两个人口 0 的同名村 | Tokyo 9,733,276 ✓ |
| `伦敦` | 加拿大安大略省伦敦（42 万） | London UK 8,961,989 ✓ |

所以每次搜索会**并行查英文索引 + 中文索引**，按 geonames id 去重合并；中文输入还会用内置城市库翻译成英文名再查一次。结果按「名称完全匹配 > 前缀 > 包含」打分，同分比人口。命中的英文条目会用内置库补回中文城市名和国家名，英文原名作为副标题显示。

### 中国区县

Open-Meteo 的地理编码只收录到地级市，搜「惠阳」返回空。本工具的处理顺序：

1. 在线搜索
2. 零结果，或命中的都是人口 < 30 万的同名村镇 → 查内置的县级行政区表，翻译成所属地级市再搜（惠阳 → 惠州，雁塔 → 西安，顺德 → 佛山）
3. 仍然没有 → 用内置的 144 座城市库做模糊匹配，界面上会明确标注这不是真实搜索结果

另外接口的中文名收录不统一（「惠州」是裸名，「佛山市」带市字），翻译时两种写法都会试。同名结果按人口降序排，避免云南一个 0 人口的「佛山」村排到广东佛山前面。

## 多语言与多历法

9 种语言：简体中文、繁體中文、English、日本語、한국어、Español、Français、Deutsch、العربية。右上角下拉切换，选择存 localStorage。阿拉伯语会把 `<html dir>` 翻成 `rtl`，样式里有 50 条镜像规则配套。

语言包在 `src/js/10-i18n.js`，取词一律走 `T('key')` / `T('key',{n:1})`。再加一种语言只需在 `LOCALES`、`LANG_NAMES`、`STRINGS` 各补一项。

**历法跟着地点走，语言兜底。** 选「跟随」时的推断顺序：

1. 看**地点**所在国有没有并行使用的传统历 —— 在北京就显示农历，哪怕界面是英文。
   农历是那个地方的属性，不是界面语言的属性
2. 没有（比如英国）→ 看**界面语言**。中文用户在伦敦仍然会看到农历
3. 都没有 → 不显示。英文界面看伦敦就是干净的公历

用户随时可以在下拉框里改成任意一种，包括「不显示」。

**节日地区同理**：在东京就看日本节日（哪怕界面是中文）；所选地点的国家不在这 28 个里
（比如肯尼亚）才退回界面语言对应的地区 —— 中文用户看中国节日，总比看一片空白有用。
「节日与假期」卡片上有下拉框可以手动指定。

**非中文界面下仍显示中文原文的部分**（专有名词，翻译反而失真）：农历月日名（七月初二）、干支生肖（丙午马年）、二十四节气（处暑）、中国传统节日（七夕节）、城市与行政区中文名。它们的**说明标签**会翻译，例如 `处暑 / Solar term`、`中秋节 / 3 days off (09/25–09/27) · statutory`。

## 气象预警

三级来源，同时显示，各自标明出处：

| 级别 | 来源 | 覆盖 | 要 key |
|---|---|---|---|
| 1 | 中央气象台 | 中国大陆，精确到县级，全灾种 | 否 |
| 1 | 香港天文台 | 香港 | 否 |
| 1 | 美国国家气象局 | 美国全境 | 否 |
| 1 | Bright Sky（转发德国气象局） | 德国 | 否 |
| 1 | 中央气象台台风网 | 西北太平洋台风 | 否 |
| 2 | 和风天气 | 全球 | 是 |
| 3 | 本地推算 | 全球，任何地方都有 | 否 |

**为什么覆盖是打补丁式的**：天时是纯静态站点，没有服务端，所有请求都从访问者浏览器发出。
浏览器会拦掉一切不发 `Access-Control-Allow-Origin` 的跨域请求，而本该填补空白的
MeteoAlarm（欧洲）和 WMO（全球）恰恰都不发这个头。所以德国以外的欧洲、南美、非洲、南亚等地区
目前只有本地推算和（可选的）和风。想扩大覆盖，欢迎来提源 —— 判据只有一条：
**免 key 且允许跨域**。可以用 `scripts/probe-alert-sources.html` 自测。

已探测过但**不可用**的：MeteoAlarm（欧洲）、WMO、印度气象局 —— 都没有跨域头；
澳大利亚气象局技术上能通，但返回值里明写 "You must not use, copy or share it"，
是明确的法律禁止，所以不接。

**中国大陆这条是怎么匹配地点的**：接口只给一个标题字符串
（「湖南省株洲市醴陵市气象台发布暴雨黄色预警信号」），省市县、灾种、级别全埋在里面。
所以是把所选地点的省/市/县名去掉「市省区县」后缀，再去标题里找。单字片段一律丢弃 ——
「东区」去掉「区」只剩「东」，会命中一大堆无关的县。

### 本地推算的边界

按中国气象局《气象灾害预警信号发布与传播办法》的阈值，从预报数据自行判断，
界面上标注「本地推算」，不冒充官方发布。覆盖高温、暴雨、大风、寒潮、降雪、雷暴，
沿用国标四色（蓝 < 黄 < 橙 < 红）。

官方标准用的是「24 小时内」「3 小时内」这类滑动窗口，而我们手上只有逐日汇总量
（日最高温、日降水总量、日最大风速），所以这是**保守的近似**，宁可少报不虚报。
官方已发布同类预警时，本地推算的那条会自动去重。

**本地推算做不了台风。** 台风预警的前提是「存在一个被命名的热带气旋，且它的路径会
影响这里」，而日最大风速区分不了台风和一场冷锋大风。所以台风必须有官方发布源。

### 台风

接的是中央气象台台风网。除预警条外还显示与所选地点的球面距离、中心风力、气压和
移动方向。**距离分级是本项目自己算的**（≤200 km 红、≤500 橙、≤900 黄、更远蓝，
再与台风等级取较小值），不是官方发布的预警级别，界面上标为「推算」。

这个接口没有公开文档，随时可能改结构。所以解析写成了结构无关的搜索：
在返回的嵌套数据里找「同时具备合理经纬度和风速」的记录，找不到就安静返回空，
不抛异常也不显示半截数据。

## 隐私与安全

- 收藏地点、主题、语言只存在浏览器 `localStorage`，不上传
- 和风的 API Host / Key（若填写）同样只存本机，不上传、不进 Git
- 除向 Open-Meteo（以及你主动启用的和风）请求天气外没有任何网络行为
- 无统计、无追踪、无广告
- 内容安全策略把 `connect-src` 锁死在天气接口域名上，即使出现 XSS 也无法把数据外传到任意域名
- 所有来自网络的字符串在进入 `innerHTML` 前都过 `esc()` 转义

> 这是一个**纯静态站点，没有服务端**。所以如果你自己部署并填入和风 Key，那把 Key 是存在**访问者自己的浏览器**里的，不会经过任何服务器——但也意味着密钥这类东西没有地方可藏。详见 [SECURITY.md](SECURITY.md)。

## 配色

两套，对应一天的两端。◐ 按钮在两者之间切换，没有别的调色板。

**蓝调时刻 Blue Hour（暗色）** —— 日落之后、天光未尽的那段时间：天空压成深蓝，
地平线还留着一线暖光。所以底色是冷的深蓝，强调色是那点残存的琥珀 —— 冷底暖点，
两者的对比正是这个时刻好看的原因。

| | 背景 | 正文 | 强调 | 次强调 |
|---|---|---|---|---|
| 蓝调时刻 | `#101623` | `#E9EDF5` | `#E9A96B` | `#7FA9DC` |
| 玫瑰黎明 | `#FDF7F4` | `#332327` | `#A8455E` | `#B35F3C` |

**玫瑰黎明 Rosy Dawn（亮色）** —— 荷马反复用的那个词，ῥοδοδάκτυλος Ἠώς，
玫瑰色手指的黎明。底色是天亮前被染红的乳白，强调色就是玫瑰色本身。

两套的每个颜色都对背景验算过 WCAG AA（正文 ≥4.5，强调与状态色 ≥3.0）。
验算写在 `npm run test:offline` 里，而且是**直接从 CSS 里读变量**再算 ——
改了颜色忘了改测试这种事不会发生。
